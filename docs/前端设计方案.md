# 海龟汤前端界面设计方案

> 设计对象：主力前端 `/`
>
> 设计依据：`docs/功能总览.md`、现有主力前端 `packages/web/public/index.html`
>
> 设计边界：除“全员讨论区”外，本方案只设计已有功能的界面与交互呈现，不增加其他玩法、接口、数据字段、角色、自动流程或后端能力。全员讨论区是本版唯一新增功能；`/deep/` 与 `/lodge/` 继续保持为相互隔离的视觉实验版。

---

## 1. 设计目标

将现有主力版从“功能平铺的深色面板”整理成一张层级清晰的“夜间推理桌”，让玩家始终先看到：

1. 当前处于哪个阶段。
2. 现在轮到谁。
3. 汤面是什么。
4. 大家已经问过什么。
5. 自己当前可以做什么。

房间配置、额度来源、API Key、成员管理等房主功能仍完整保留，但降低视觉优先级，避免干扰普通玩家推理。

本方案不改变以下既有规则：

- 三套前端的资源和 localStorage 键继续隔离。
- 房间状态由 D1、客户端轮询和每请求惰性补算共同推进。
- 房主不需要准备；离线、旁观者和房主不计入准备分母。
- 汤底在猜中前不向任何人下发。
- 猜中时对全桌公示汤底。
- 中止对局不公示汤底。
- 猜汤底使用全桌共用冷却。
- AI 调用失败不自动切换平台额度。
- 临时启用平台额度仍需全员投票。
- API Key 明文无法回读。

---

## 2. 视觉方向与区域格式

### 2.1 核心美术概念：深夜档案桌

界面不采用常见 AI 产品的蓝紫渐变、玻璃拟态、大面积霓虹光晕和悬浮胶囊。主力版应像一张正在使用的深夜推理档案桌：

- 页面底层是墨蓝黑色桌面，不做宇宙渐变背景。
- 汤面像一张放在桌心的暖灰案卷纸，是全页唯一的大面积浅色区域。
- 正式提问记录像逐条装订的审讯记录，答案使用印章式标记。
- 全员讨论像桌边便笺，不和正式档案使用同一种格式。
- 当前回合像机械计时牌，强调数字、刻度与真实推进感。
- 房号像档案编号；角色和状态像窄小的纸签或橡皮章，而不是圆润的彩色胶囊。

这种风格的重点不是复古装饰，而是用“案卷、批注、印章、索引、计时牌”建立信息身份：玩家无需阅读标题，也能从材质和格式区分汤面、正式记录、聊天与管理信息。

### 2.2 风格禁区

实现时明确避免以下通用化表现：

- 不使用蓝紫色大面积渐变作为品牌主体。
- 不使用每张卡片都半透明、模糊和发光的玻璃拟态。
- 不给所有按钮做渐变填充和外发光。
- 不把所有标签都做成同样的圆角胶囊。
- 不使用机器人、魔法星光、AI 脑图、赛博网格等现成 AI 意象。
- 不用无意义的大标题、营销标语和大面积留白撑页面。
- 不用随机漂浮粒子、持续扫光和循环渐变制造“科技感”。
- 不用 emoji 充当所有功能图标；海龟标志可保留，但功能图标统一使用单色线性图标或文字。

### 2.3 色彩系统

色彩来自深夜桌面、旧纸、铅笔、印泥和黄铜，而不是 AI 产品常见的冷艳霓虹色。

```css
:root {
  /* 桌面与结构 */
  --desk-950: #0b1012;
  --desk-900: #11191b;
  --desk-800: #182225;
  --desk-700: #223034;
  --rule-dark: #344347;

  /* 案卷纸 */
  --paper-100: #eee9dc;
  --paper-200: #ded7c7;
  --paper-300: #c8bfad;
  --ink-900: #202526;
  --ink-600: #596264;

  /* 功能色 */
  --brass: #b99255;
  --brass-light: #d4b477;
  --stamp-yes: #287b68;
  --stamp-no: #a64e45;
  --stamp-unknown: #a5742f;
  --stamp-irrelevant: #647176;
  --signal: #83a69e;
  --danger: #bd554b;

  /* 文本 */
  --text-on-dark: #e9e5da;
  --text-secondary: #aeb8b6;
  --text-muted: #75817f;

  /* 交互 */
  --focus: #d4b477;
  --selection: rgba(185, 146, 85, 0.28);
}
```

使用规则：

- 暖纸色只用于汤面、汤底和重要复盘正文，形成明确视觉中心。
- 黄铜色只用于主操作、当前回合刻度、选中页签和房号。
- 青绿色只用于“是”、准备完成、连接正常和成功状态。
- 印泥红只用于“不是”、错误和危险操作。
- 琥珀色用于“无法回答”、宽限期、冷却和待处理状态。
- 灰蓝色用于“与此无关”、次要说明和禁用状态。
- 色彩必须与文字、形状或图标共同表达含义。

### 2.4 字体系统

不引入外部字体，使用系统字体组合，但通过不同字体栈塑造区域身份：

```css
/* 界面与正文 */
--font-ui: -apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", system-ui, sans-serif;

/* 房号、时间、回合序号、技术信息 */
--font-mono: "Cascadia Mono", "SFMono-Regular", Consolas, monospace;

/* 汤面和汤底标题；使用系统宋体形成案卷感 */
--font-story: "Songti SC", SimSun, serif;
```

| 内容 | 字号／行高 | 格式 |
|---|---|---|
| 品牌名 | 18 px / 1.2 | 700，字距 0.06em |
| 区域眉题 | 11 px / 1 | 700，字距 0.16em，使用黄铜或灰色 |
| 汤面标题 | 24 px / 1.35 | 宋体，700 |
| 汤面正文 | 17 px / 1.95 | 暖纸上的深墨色，最大行宽 42em |
| 正式问题 | 15 px / 1.7 | 500 |
| 聊天正文 | 14 px / 1.6 | 400 |
| 倒计时 | 32 px / 1 | 等宽字体，700，表格数字 |
| 房号 | 15 px / 1 | 等宽字体，字距 0.18em |
| 辅助信息 | 12 px / 1.5 | 400 |

### 2.5 形状、边框和层级

- 桌面区域使用 2–4 px 小圆角或直角，不使用到处都是 16–24 px 的大圆角。
- 汤面纸张可使用 2 px 圆角和轻微不规则阴影，像平放的纸，不模拟卷边和破损。
- 普通深色面板用 `1px solid var(--rule-dark)`，标题区域使用短横线或编号分隔。
- 主操作按钮使用黄铜实色、深色文字、4 px 圆角；次按钮使用透明底和细边框。
- 危险按钮默认只是红色文字和边框，确认后才使用红色实底。
- 标签分三类：身份用窄纸签，状态用方角印章，题目属性用短横线分隔的文本标签。三类不能共用一种胶囊样式。
- 阴影只用于纸张、弹窗和吸底操作区；普通面板不加悬浮阴影。

### 2.6 页面背景

背景使用近黑墨蓝纯色，并通过非常弱的 CSS 纹理表现桌面纤维：

```css
body {
  background-color: var(--desk-950);
  background-image:
    linear-gradient(rgba(255,255,255,.012) 1px, transparent 1px),
    linear-gradient(90deg, rgba(255,255,255,.008) 1px, transparent 1px);
  background-size: 24px 24px;
}
```

纹理对比度必须低到不影响阅读；不使用径向霓虹光斑。页面中心可以有一层固定宽度的深色工作台，不使用全页漂浮卡片。

### 2.7 顶栏风格

顶栏像档案柜的索引条，而不是网站导航栏：

- 高度 56–60 px，深色实底，底部一条黄铜细线。
- 左侧海龟标志做成 28 px 单色图章，旁边是“海龟汤”和小号“情境推理档案”。
- 房号区域格式为 `ROOM / K7M2QX`，使用等宽字体，点击整个编号复制。
- 连接状态使用直径 6 px 的信号灯和短文字，不做发光圆点。
- 右侧“房间信息与设置”使用带三条索引线的文字按钮。
- 移动端只保留标志、房号、连接灯和设置图标，不压缩成多行。

### 2.8 入口页风格

入口页设计成“建立档案／进入档案”工作台：

- 左侧不是营销 Hero，而是一张竖向案卷封面，写游戏名、三步玩法和保密说明。
- 案卷封面使用暖灰纸色，左上角盖一个小型海龟印章，底部印“猜中前密封”。
- 右侧表单是深色登记台，字段标签用“玩家署名”“房间编号”等简洁文案。
- 输入框为深色底加单条下边线，聚焦时下边线变黄铜色，不使用发光描边。
- 快速／标准／休闲像三张并排索引卡：左上角写 `01/02/03`，选中后出现黄铜订书钉式标记。
- 主按钮写“创建 / 加入”，做成盖章器式方角按钮；恢复房间使用纯文字次按钮。
- 服务端模型和保险箱状态放在表单最下方的“设备状态”小字区，不进入主视觉。

### 2.9 当前回合区风格

当前回合区像桌边机械计时牌：

- 顶部眉题为 `TURN / 当前回合`。
- 发言者头像不使用彩色渐变，改为深色方牌加暖白首字。
- 昵称是区域内最大文字，下面显示“正在提问／宽限期／判定中”。
- 倒计时使用等宽大数字，格式固定为 `00:42`。
- 进度条不是圆润胶囊，而是一排 20–30 个细刻度；时间减少时从右向左熄灭。
- 轮到本人时，左边缘出现一条黄铜标尺，并显示“你的回合”方角纸签。
- 最后 5 秒不闪整块区域，只让数字和最后几格刻度变为印泥红。
- 等待阶段沿用同一区域，机械计时牌切换为“落座记录”，展示准备人数和准备按钮。

### 2.10 汤面区域风格

汤面是全页面唯一的“大纸张”：

- 使用 `paper-100` 暖灰底、深墨文字和极轻纸张阴影。
- 顶部左侧印 `CASE SURFACE / 汤面`，右侧是题目属性，不使用彩色胶囊。
- 题目标题用系统宋体，标题下方一条细墨线。
- 汤面正文保持充足行距和 42em 最大行宽，短文本也不垂直居中。
- L1–L3 使用小型方形分级章；难度使用五个短竖刻度；预计时长使用等宽数字。
- 普通标签用 `#标签` 纯文本；敏感标签使用细红框并写“内容提示”。
- 题库来源放在纸张底部，像档案出处脚注。
- 提示和猜汤底不放进正文纸张内部，而放在纸张下方的“案卷工具条”，保持故事内容纯净。

### 2.11 统计区风格

提问、线索、提示和探索度做成一条“档案索引尺”：

- 不使用四张独立统计卡。
- 用一条水平细线串联四组数据，每组由大数字和小标签组成。
- 数字使用等宽字体；单位和说明使用 11–12 px。
- 探索度用细刻度尺，不使用亮色渐变进度条。
- 移动端允许横向两行排列，但保持同一背景，不拆成小卡片矩阵。

### 2.12 公共记录风格

公共记录像装订的审讯记录册：

- 区域标题为 `LOG / 正式记录`，旁边显示记录数量。
- 每条问答使用上下分区，而不是聊天气泡。
- 第一行是回合编号、提问者和时间；第二行是完整问题；右侧或下方盖答案章。
- “是／不是／与此无关／无法回答”使用略带旋转角度的方形印章，但文字始终水平可读。
- 自己的提问在左侧增加一条黄铜装订线，并写小号“本人”。
- 判定来源像脚注编号，使用小号等宽文字，不做彩色标签。
- 服务端解释使用铅笔批注样式：灰色文字、左侧短线、略小字号，不使用斜体大段引用。
- 系统事件使用横跨记录区的细分隔线和居中文字，不伪装成普通消息。
- 被拒绝事件使用红色批注边线，不铺大面积红底。

### 2.13 全员讨论区风格

讨论区像贴在档案桌边的便笺栏，与正式记录有明显差异：

- 页签标题用 `NOTES / 全员讨论`，未读数像右上角手写圈号。
- 其他玩家消息使用灰绿便笺底，自己的消息使用偏暖黄褐便笺底。
- 气泡只使用 4 px 小圆角，尾巴可省略；避免即时通讯软件式的大圆泡。
- 昵称、时间在消息上方使用 11 px 等宽字；正文保持正常中文字体。
- 同一玩家的连续消息共享一次头像和昵称，形成便笺组。
- 输入框像便笺底部的书写横线，发送按钮是小型“贴上”方按钮。
- 新消息入口写“↓ 3 条新便笺”，不使用悬浮蓝色圆按钮。
- 移动端讨论面板保留深色桌面背景，消息便笺居中排列，不把整个页面做成白色聊天应用。

### 2.14 玩家区风格

玩家列表像案件参与人员名册：

- 标题为 `CREW / 在桌成员`，右侧显示人数。
- 每行固定高度 48–52 px，使用细横线分隔，不为每人创建独立卡片。
- 头像是 28–32 px 方形姓名牌，颜色来自一组低饱和固定色，不使用随机彩虹渐变。
- 房主身份使用黄铜钥匙形小图标加“房主”；原房主使用空心钥匙。
- 在线状态是姓名牌角落的小圆点；挂机为琥珀，断连为空心灰点。
- “已准备”使用青绿色对勾和文字；“未准备”只用灰字，不用警告红。
- 当前发言者整行左侧出现黄铜刻度线。
- “移出”默认藏在行尾的更多操作中，展开后才显示红色文字。

### 2.15 正式提问操作区风格

底部操作区像档案桌前缘的一块书写板：

- 使用不透明 `desk-900`，顶部一条黄铜细线，不使用模糊玻璃背景。
- 左上角清楚写 `ASK / 正式提问`，旁边注明“发送后公开且不可撤回”。
- 文本框使用深色平面和底线，最少两行；聚焦时只改变底线和光标颜色。
- “发送”是唯一黄铜实底主按钮。
- “猜汤底”使用印泥红细框，“讨论”使用便笺图标和未读圈号，三者形状明显不同。
- 未轮到本人时，不把整个区域降到 40% 透明；输入仍可用，仅发送按钮显示“等待回合”。
- 宽限期时顶部细线变为琥珀色，并显示“宽限期内仍有效”。

### 2.16 提示工具风格

T1、T2、T3 像从浅到深的三枚档案索引签：

- 三个按钮使用相同尺寸的方形纸签，不使用三个彩色胶囊。
- T1 为浅灰绿，T2 为黄褐，T3 为暗红褐，体现提示强度但不过度抢眼。
- 按钮同时显示 `T1/T2/T3` 和小号中文“轻／中／深”。
- 配额与冷却写在工具条下方，不把数字塞进按钮。
- 提示关闭时只保留一行细灰字和房主参数入口，不留空白按钮位。

### 2.17 猜汤底弹窗风格

猜汤底应像提交一份“结案陈词”：

- 弹窗顶部写 `FINAL THEORY / 结案推理`，而不是普通表单标题。
- 内容背景仍为深色，中央输入区使用一张暖灰稿纸，带淡淡横线。
- 判定标准和共用冷却放在稿纸上方的两条说明中，重点数字使用等宽字体。
- 主按钮使用印泥红实底并写“提交推理 · 揭晓”。
- 返回按钮为无底色文字。
- 冷却中在提交位置显示机械倒计时，不显示一个灰掉的普通按钮。

### 2.18 房间信息、额度与 AI 状态风格

这些区域属于“设备与管理”，统一使用冷静的仪表铭牌格式：

- 背景使用 `desk-800`，直角边框和等宽小字，不使用纸张材质。
- AI 状态前使用实体信号灯：正常青绿、模拟琥珀、异常红色、暂停灰色。
- 当前额度模式作为铭牌主值，原因码放在下一行小字。
- Key 掩码使用等宽字体，放在带凹槽感的深色条内。
- “更新 Key”“撤销 Key”等操作使用文字按钮，不和对局主操作竞争。
- AI 异常提示像贴在设备上的维修单：左侧红线、故障摘要、处理按钮；不做大面积警告渐变。

### 2.19 参数和 API Key 弹窗风格

管理弹窗像一本打开的设备手册：

- 桌面端宽度 680–760 px，深色实底，顶部黄铜编号线。
- 标题左侧显示章节编号，如 `SETTINGS / 01`。
- 参数按“回合、猜底、提示、选题”分组，每组使用左侧窄索引，不堆叠大量独立卡片。
- 数字输入框使用等宽字体；开关使用短拨杆式外观，不使用手机系统风格的大滑块。
- API Key 输入区像设备接线表：提供方、地址、模型和 Key 按顺序垂直排列。
- 测试结果使用“检测通过／检测失败”印章和技术明细，不用绿色或红色大色块。
- 弹窗底部操作栏固定，主操作在右，关闭在左。

### 2.20 汤底公示风格

汤底公示与普通弹窗必须有明显差异，形成唯一的仪式时刻：

- 背景先压暗，不使用烟花、彩纸或 AI 粒子动画。
- 中央出现一只横向封套，封条从中间向两侧退开，露出暖纸色汤底。
- 顶部盖一枚青绿色“已解开”印章；标题使用宋体“汤底”。
- 汤底正文保持高可读性，不逐字打字，不做模糊解密特效。
- 动画结束后成为普通可滚动纸张；减少动态效果时直接显示最终状态。
- 房主“回到选题”使用黄铜按钮，普通玩家只有“返回桌面”。
- 页面内长期保留的汤底卡片沿用同一纸张语言，但去掉开封动画。

### 2.21 复盘风格

复盘像一份结案档案：

- 顶部是案件名称、结果、原因和提问总数。
- 汤底使用暖纸区；问题与判定使用正式记录格式；成员数据使用名册表格。
- 不使用仪表盘饼图、发光数字或无实际数据依据的图表。
- 长内容依靠清晰章节、编号和横线分隔。
- “仅房主可见”使用顶部固定的红色窄条提示，不占用正文空间。

### 2.22 投票、候选题与 AI 创作风格

- 候选题像并排的案卷摘要卡：纸灰底、编号、汤面摘要和底部属性行。
- 被选中的题在左上角盖黄铜“选中”章，不使用发光边框。
- 投票进度用纸卡顶部的一排短刻度与 `已投 2/4`，倒计时使用等宽字。
- “投给这道”使用窄边框按钮；投票后改为盖章式“已投”。
- AI 创作区仍归类为设备区，不使用机器人头像；生成中显示逐行打印的占位横线。
- 质检失败像退回单，列出路径和原因；通过后在候选纸卡上盖“质检通过”。

### 2.23 通知与错误风格

- 短提示从右上角像一张窄收据滑入，宽度 280–320 px，停留后收起。
- 成功通知左侧是青绿短线，警告为琥珀短线，错误为红色短线。
- 持续状态嵌入相关区域顶部，不用全页面反复出现相同提示。
- 错误文案先给人话结论，技术原因码使用下一行等宽小字。
- 不使用大面积纯色背景，也不在每条提示前堆 emoji。

### 2.24 动效语言

动效模拟真实物件的短动作，不模拟 AI 能量流：

- 新正式记录像纸张向下增加 6 px 后归位，持续 160 ms。
- 新讨论消息像便笺贴入，持续 140 ms。
- 页签切换只做内容淡入，不左右飞屏。
- 当前回合变化时，计时刻度先清空再从满格开始。
- 按钮按下时下移 1 px，不上浮、不发光。
- 汤底开封是唯一可超过 300 ms 的动画，控制在 700–900 ms。
- `prefers-reduced-motion` 下移除位移、呼吸和开封过程，保留状态颜色变化。

所有视觉动画只表现现有状态，不改变计时、轮询或状态推进逻辑。

### 2.26 基础控件格式

#### 按钮

| 类型 | 样式 | 使用场景 |
|---|---|---|
| 主按钮 | 黄铜实底、深色字、4 px 圆角、无渐变 | 创建／加入、发送问题、保存参数、下一局 |
| 次按钮 | 透明底、灰色细边、暖白字 | 复制、返回、关闭、测试连接 |
| 便笺按钮 | 黄褐浅底、深墨字 | 打开讨论、发送聊天 |
| 推理按钮 | 印泥红边框，确认态才实底 | 猜汤底、提交推理 |
| 危险按钮 | 默认红字无底，确认弹窗内红色实底 | 移出、结束、销毁 Key |
| 禁用按钮 | 保留边界，文字变灰，不整体降低透明度 | 等待回合、冷却、配额耗尽 |

按钮高度桌面端 36–40 px，移动端至少 44 px。按钮文本保持具体动作，不只显示图标。

#### 输入框

- 普通输入：深色平面、单条底边、无内阴影。
- 汤底推理输入：暖纸稿面、淡横线、深墨字。
- Key 输入：等宽字体、深色凹槽、显隐按钮位于字段尾部。
- 错误状态：底边变为印泥红，并在下方显示一行原因；不让整个字段震动。
- 聚焦状态：底边变黄铜色，外部只加 2 px 可访问焦点线，不做霓虹发光。

#### 页签

- 页签使用文字和底部短线，不使用填充胶囊。
- 选中项为暖白字和黄铜短线；未选中项为灰字。
- 未读数使用 16–18 px 圈号，贴在“讨论”文字右上角。
- 桌面端“玩家／讨论”和移动端“记录／讨论”使用同一套页签语言。

#### 标签与印章

- 身份纸签：房主、原房主、旁观者，窄矩形，浅底深字。
- 状态印章：已准备、发言中、已暂停、已投，方角描边。
- 答案印章：是、不是、与此无关、无法回答，较粗边框和固定宽度。
- 属性文本：L 等级、难度、时长、标签，使用分隔点或短竖线，不加容器。
- 同一区域最多同时出现两种标签形式，避免视觉噪声。

#### 弹窗与抽屉

- 遮罩使用纯黑 68% 透明度，不加背景模糊。
- 弹窗使用深色实底、1 px 边框和窄阴影，圆角不超过 6 px。
- 桌面弹窗居中；移动端参数、Key、复盘使用近全屏页面，讨论使用全高面板。
- 标题栏和底部操作栏固定，中间内容独立滚动。
- 关闭按钮固定在左侧或右上角，所有弹窗位置保持一致。

#### 图标

- 使用 1.5 px 单色线性图标，默认 16 px，重要入口 18–20 px。
- 图标只辅助文字，不代替“发送”“猜汤底”“离开”等关键动作名称。
- 海龟图章是唯一品牌插画；其余区域不增加机器人、灯泡人物或装饰插画。

右侧栏使用“玩家／讨论”两个页签，避免自由聊天挤占汤面和正式问答记录。

“玩家”页签展示现有成员数据：

- 头像与昵称。
- 在线、挂机或断连状态。
- 房主、原房主、旁观者身份。
- 准备状态。
- 当前发言者。
- 分数。
- 房主可见的“移出”操作。

“移出”放在玩家行尾部，使用危险样式并保留确认步骤，避免误触。

“讨论”页签展示新增的全员文字消息：

- 页签上显示未读数量，如“讨论 3”。
- 中间为可滚动的消息列表。
- 底部固定单行输入框和发送按钮。
- 自己的消息右对齐，其他玩家的消息左对齐并显示头像、昵称和时间。
- 切换页签不影响中央公共记录的滚动位置，也不清空尚未发送的聊天草稿。

- 对局进行中固定在页面底部。
- 提问框允许提前输入草稿。
- 草稿继续只存本机，不上传、不广播。
- 未轮到本人时发送按钮禁用，并显示正在等待谁发言。
- 轮到本人时突出发送按钮。
- 宽限期内按钮文案显示“发送（宽限期内仍有效）”。
- 猜汤底按钮在对局进行中保持可见。
- 共用冷却期间直接在按钮上显示剩余时间。

## 12. 全员讨论区（新增）

### 12.1 功能定位

讨论区用于同一房间内的所有成员自由发送文字消息，例如商量下一步问什么、整理推理方向或提醒队友。它在等待、选题、投票、对局进行、暂停和本局结束阶段都可使用；进入下一局后仍留在同一房间讨论。

该功能不取代正式提问：

- 聊天消息不提交给 AI 主持人。
- 不占用提问回合。
- 不进入判定缓存。
- 不增加线索或探索度。
- 不会触发猜汤底判定。
- 需要主持人回答的问题仍必须由轮到的玩家通过正式提问框发送。

### 12.2 可用角色

- 房主、普通玩家、原房主均可查看和发送。
- 房间允许旁观时，旁观者也可查看和发送，便于所有房间成员共同讨论。
- 离席或被移出后，原会话立即失去继续读取和发送消息的权限。
- 讨论区不提供私聊，所有消息对当前房间成员可见。

### 12.3 桌面端

桌面端放在右侧栏的“讨论”页签中，与“玩家”页签并列：

```text
┌─────────────────────────────┐
│ [玩家 4]  [讨论 3]          │
├─────────────────────────────┤
│ 阿伟                 21:32  │
│ 先问一下门是不是锁着的。    │
│                             │
│                你    21:33  │
│ 我觉得照片里的时间更重要。  │
│                             │
│ 七喜                 21:33  │
│ 下一轮我来问照片。          │
├─────────────────────────────┤
│ 发消息…              [发送] │
└─────────────────────────────┘
```

布局要求：

- 右侧栏宽度建议 300–340 px。
- 消息列表占据剩余高度并独立滚动。
- 输入区固定在讨论栏底部。
- 按 Enter 发送，Shift+Enter 换行；输入法组字期间按 Enter 不得误发送。
- 讨论页签未打开时，新消息只增加未读数字。
- 打开讨论页签并滚动到底部后，清除未读数字。
- 玩家正在查看旧消息时，不强制滚到底部，显示“有新消息”入口。

### 12.4 移动端

移动端提供两个入口：

- 公共记录标题旁的“讨论”页签。
- 底部提问操作区中的“讨论”按钮，并显示未读数字。

点击后打开接近全屏的讨论面板：

```text
┌──────────────────────────┐
│ ← 返回  全员讨论  K7M2QX │
├──────────────────────────┤
│ 阿伟  21:32              │
│ 先问门是不是锁着的。      │
│                          │
│              你  21:33   │
│ 我觉得时间更重要。        │
│                          │
│ 七喜  21:33              │
│ 下一轮我来问照片。        │
├──────────────────────────┤
│ 发消息……          [发送] │
└──────────────────────────┘
```

移动端要求：

- 面板使用可视视口高度，软键盘弹出后输入区仍保持可见。
- 顶部“返回”关闭讨论面板，不触发浏览器离开房间。
- 关闭后恢复原页面滚动位置、提问草稿和焦点状态。
- 消息输入草稿与正式提问草稿使用不同状态，互不覆盖。
- 收到新消息时不抢焦点、不自动打开面板、不打断正式提问输入。
- 正在讨论时仍在顶部用紧凑状态条显示当前发言者和剩余时间，避免玩家错过自己的回合。

### 12.5 消息样式

每条消息展示：

- 发送者头像。
- 发送者昵称。
- 发送时间。
- 消息正文。
- “你”标记。

视觉规则：

- 自己的消息右对齐，使用偏暖黄褐便笺底和深墨文字。
- 其他成员消息左对齐，使用灰绿便笺底和暖白文字。
- 连续由同一人发送且间隔较短的消息可合并头像区域，但每条仍保留可识别的时间信息。
- 长文本自动换行，连续字符和长链接不能撑破布局。
- 消息只按纯文本渲染，禁止把用户内容作为 HTML 注入。
- 系统事件、正式问题和 AI 判定不复制进讨论区。

### 12.6 输入与发送状态

- 输入为空或全是空白时，发送按钮禁用。
- 单条消息建议限制为 500 个字符，并显示剩余字数。
- 点击发送后显示局部发送中状态，防止重复提交。
- 发送成功后清空讨论草稿，并立即显示服务端返回的消息。
- 发送失败时保留草稿，在输入区上方显示失败原因和“重新发送”。
- 每次发送使用客户端消息 ID，避免网络重试产生重复消息。
- 讨论草稿只保存在当前页面内存中，不与 `ht.draft` 的正式提问草稿共用。

### 12.7 未读与滚动

- 未读数量显示在桌面端“讨论”页签和移动端“讨论”按钮上。
- 未读数只计算其他成员发送、且当前用户尚未看到的消息。
- 数量超过 99 时显示 `99+`。
- 用户正停留在讨论区底部时，新消息自动滚入视野并视为已读。
- 用户向上阅读时保持当前位置，并显示“有 N 条新消息”。
- 未读状态仅用于前端提示，不改变房间或对局状态。

### 12.8 生命周期与安全边界

- 消息属于房间，不属于某一回合；下一局开始后旧消息仍可查看，并用“第 N 局开始”分隔线区分。
- 最后一人离开或房间过期被清理时，讨论消息随房间一起清理。
- 服务端不得把未公开的汤底、事实点或 Key 明文拼入讨论消息响应；讨论接口只接收并返回成员输入的纯文本和必要的发送者元数据。
- 昵称继续使用现有清洗规则；消息正文需要长度限制、控制字符清理和输出转义。
- 讨论发送需要独立限流，避免刷屏，但限流不得影响正式提问、心跳或其他对局动作。

### 12.9 最小数据与接口约定

这是新增功能落地时唯一需要补充的后端能力。建议消息结构保持最小化：

```ts
type ChatMessage = {
  id: string;
  roomId: string;
  memberId: string;
  memberName: string;
  text: string;
  clientMessageId: string;
  createdAt: number;
};
```

建议在现有轮询体系中扩展，而不是增加 WebSocket：

- 发送：在现有 `/api/rooms/actions` 中增加 `chat` 动作，提交 `text` 与 `clientMessageId`。
- 接收：`GET /api/rooms/state?since=` 的增量载荷增加 `chatMessages`，复用已有轮询与事件序号。
- 动作响应：发送成功后直接带回规范化后的消息，使发送者无需等待下一轮轮询。
- 权限：沿用 Bearer 会话令牌，只允许当前房间成员读取和发送。
- 持久化：新增房间消息存储，房间物理清理时一并删除。

界面不需要也不设计以下能力：

- 私聊。
- 图片、文件、语音或富文本。
- 表情回应。
- 编辑或撤回消息。
- 消息搜索。
- 跨房间聊天。

界面顺序：

```text
提供方
Base URL
实际请求地址
模型名
API Key
显示／隐藏
连接测试结果
测试连接（不入库）｜连接测试并提交｜撤销并销毁
```

安全呈现保持现有规则：

- Key 明文只在当前页面内存中。
- 不写入浏览器存储。
- 服务端保险箱未开启时不能提交保存。
- 提交后页面只显示掩码。
- 任何角色都无法回读明文。
- 关闭弹窗时清除 Key 明文草稿。

## 24. 与现有实现的对应关系

以下现有实现应直接保留：

- `ht.token`、`ht.draft` 和昵称本地存储。
- 服务端时间偏移驱动倒计时。
- 250 ms 的轻量倒计时界面更新。
- 1.2 秒房间状态轮询。
- 动作响应直接带回最新视图。
- 会话代次丢弃离席后的迟到响应。
- 用户输入、中文输入法组字、拖动和文本选择期间推迟整页重渲染。
- 状态指纹排除持续变化的服务端时间。
- 记录是否贴底的滚动保护。
- 输入焦点、光标位置和弹窗滚动位置恢复。
- 移动端输入框吸底。
- Key 明文不写入浏览器存储。
- 猜中后自动弹出汤底，并在页面保留汤底卡片。

新增讨论区实现时需要在现有状态之外补充：

- `chatMessages`：当前房间已加载的讨论消息。
- `chatDraft`：独立于正式提问的讨论草稿。
- `chatUnread`：其他成员消息的未读数量。
- `chatOpen`：桌面讨论页签或移动讨论面板状态。
- `chatPinned`：讨论列表是否停在底部。
- `chatSending`：当前发送请求状态。

讨论消息应复用现有会话代次、轮询、状态应用和迟到响应保护，避免离开房间后旧消息重新写入页面。

界面重构重点：

1. 提高汤面、当前回合、记录和输入区的视觉优先级。
2. 降低房间元数据、额度和技术原因码的视觉优先级。
3. 将英文内部状态统一转换为中文界面文案。
4. 按等待、进行、暂停和结束阶段组织已有卡片。
5. 桌面端使用明确的三栏层级，移动端沿用玩法顺序。
6. 对局参数严格使用功能总览中的现行字段，不保留旧参数名称。
7. 保留所有现有安全、竞态和输入保护逻辑。

## 25. 界面验收清单

### 视觉风格

- [ ] 页面整体能明确识别为“深夜档案桌”，而不是通用 AI 控制台。
- [ ] 页面背景没有蓝紫霓虹光斑、漂浮粒子或赛博网格。
- [ ] 汤面和汤底是主要暖纸区域，其他功能不会滥用纸张材质。
- [ ] 正式记录、全员讨论、玩家名册和设备管理具有不同视觉格式。
- [ ] 公共记录使用答案印章，不设计成聊天气泡。
- [ ] 全员讨论使用便笺组，不与正式记录混淆。
- [ ] 当前回合使用机械数字和刻度，不使用普通渐变进度条。
- [ ] 身份、状态、题目属性没有全部套用同一种胶囊标签。
- [ ] 主按钮没有渐变和外发光，且只有当前最重要操作使用黄铜实底。
- [ ] 普通面板不使用玻璃模糊和悬浮阴影。
- [ ] 功能图标统一为单色线性风格，不用 emoji 拼装界面。
- [ ] 桌面端像同时摆放不同档案物件，移动端像依次翻阅档案，而不是统一圆角卡片列表。

### 入口页

- [ ] 可以输入昵称。
- [ ] 房间码为空时创建房间，填写时加入房间。
- [ ] 可以选择快速、标准或休闲预设。

- [ ] 普通玩家可以准备和取消准备。

- [ ] 房主可随机开局、直接选题、投票选汤或使用 AI 题目。
- [ ] 强制开局前点名未准备成员。

### 对局

- [ ] 汤面、当前发言者、倒计时和公共记录处于主要视觉区域。
- [ ] 玩家可以提前输入草稿。
- [ ] 未轮到时不能发送，宽限期内仍可发送。
- [ ] 提问发出后立即公开且无法撤回。
- [ ] 问答记录显示四种判定及判定来源。
- [ ] 提示按钮遵守开关、配额、T3 上限与冷却。

### 全员讨论

- [ ] 所有当前房间成员都可以查看并发送纯文字消息。
- [ ] 桌面端可在右侧栏的“玩家／讨论”页签之间切换。
- [ ] 移动端可以从记录区或吸底操作区打开讨论面板。
- [ ] 聊天消息不进入公共记录，不占提问回合，也不影响判定、线索和探索度。
- [ ] 讨论草稿与正式提问草稿互不覆盖。

- [ ] 发送失败保留草稿并允许重新发送，重试不会生成重复消息。
- [ ] 移动端软键盘不遮挡讨论输入框。
- [ ] 打开和关闭讨论不会丢失提问草稿、页面滚动位置或当前回合提示。
- [ ] 离席、被移出或房间被清理后不能继续读取和发送讨论消息。
- [ ] 消息按纯文本安全渲染，长文本不会撑破布局。

### 猜汤底

- [ ] 对局中可以随时打开猜汤底弹窗。
- [ ] 全桌共用冷却及剩余时间清晰可见。
- [ ] 每次猜测都会按现有规则重置冷却。
- [ ] 接近时不显示事实点明细。
- [ ] 猜中后全桌看到汤底弹窗和页面汤底卡片。
- [ ] 中止对局不显示汤底。

### 房主功能

- [ ] 可修改现有全部对局参数。
- [ ] 可跳过当前回合和结束本局。
- [ ] 可移出其他成员。
- [ ] 可配置、测试、提交和撤销 API Key。

- [ ] 房主断连后显示移交状态。
- [ ] 新房主可继续对局。
- [ ] 原房主回来后可归还或拒绝归还。

### 移动端与稳定性

- [ ] 360 px 宽度下可完成现有全部核心玩法操作。
- [ ] 手机键盘不遮挡输入框和发送按钮。
- [ ] 轮询不会打断输入、选区或滚动。

- [ ] 网络中断时保留当前页面并显示正在重试。

## 26. 最终界面定位

主力版 `/` 应成为三套前端中功能最完整、信息最清楚的一套。除本方案明确新增的全员讨论区外，不扩展其他玩法；所有区域按真实对局顺序重新组织：

```text
创建或加入
→ 等待与准备，并可进行全员讨论
→ 房主选题／投票／AI 创作
→ 轮流提问与判定，同时可自由讨论
→ 使用提示或猜汤底
→ 猜中后全桌公示，或中止但不揭晓
→ 房主复盘或开启下一局
```

最终设计重点是让已有功能更容易找到、理解和操作，同时严格保持当前后端规则、权限边界与保密约束不变。
