# 实现说明与「与规划的偏差」清单

本文件回答两件事：**这套代码是怎么组织的**，以及 **哪些地方偏离了 `../产出/` 里的规划、为什么**。
规划本身没有改（它是验收基准），偏差都在这里逐条记录，避免"文档说一套、代码做一套"。

---

## 1. 运行方式：零构建、零转译

Node 24 原生支持 TypeScript 类型剥离（`node file.ts` 直接可跑），`node --test` 也能直接发现 `.ts` 测试文件。
因此本项目**没有构建步骤**：

- 服务端：`node packages/server/src/index.ts`
- 测试：`node --test`
- 类型检查：`tsc --noEmit`（只做检查，不产出 JS）

代价与约束：只能用"可擦除语法"（不能使用 `enum` / `namespace` / 参数属性等），相对导入必须写 `.ts` 后缀。
这些约束已经写进 `tsconfig.json`（`erasableSyntaxOnly: true`）与代码风格里。

**为什么这么做**：规划里「两版复用同一份核心规则」是硬要求（《阶段5》§7）。没有构建链时，
`packages/core` 既可以被子进程直接 import，也可以被未来的 Vite 客户端打包，复用的是**同一份源码**而不是复制品。
少一层构建，也就少一类"产物与源码不一致"的漂移。

## 2. 依赖与规划的差异

| 规划 | 实现 | 理由 |
|---|---|---|
| Fastify | `node:http` + 极简路由 | 路由只有 7 个端点；Fastify 的 schema/插件体系在这里是净成本。**保留其精神**：所有入参都在 handler 里显式校验，非法值整批拒绝。 |
| Socket.IO | `ws` + 自研协议（`seq` / 快照 / 心跳） | 《阶段5》§1.3 要求"事件流 + 实体版本"的收敛规则，这部分无论用哪个库都要自己实现；Socket.IO 的重连只是传输层重连，而业务层重连必须重建状态。用 `ws` 让协议与顺序完全可控、可测。 |
| better-sqlite3 | `node:sqlite`（Node 内置） | 同一个 SQLite，但**没有原生依赖**，`pnpm install` 不会因为编译工具链失败。仓储接口是自定义的，换回 better-sqlite3 只需替换 `Store` 内部实现。 |
| React + Vite + Tailwind（前端） | 阶段性零依赖单页（`packages/web/public`） | 先把"能真正联机试玩"跑通再上框架。**这是当前最大的待办**：正式客户端按规划做 React + Vite，构建产物仍输出到 `packages/web/public`（目录已就位），服务端静态托管不需要改。 |
| 单例 Server 类 | `App` + `RoomRegistry` + `RoomRuntime` | 与规划的目录树一致：`core`（规则）/ `server`（编排与 IO）/ `web`（视图）。`RoomRuntime` 就是"房间级串行队列 + 事件缓冲 + 落库"的落地。 |

## 3. 关键实现决策

### 3.1 判定：模型只做映射，答案由事实表裁决

`packages/core/src/verdict.ts` 与 `facts.ts` 保证了三件事：

1. **L0 预检**（注入/编码/索取/元提问/列举/开放提问）命中时**不调用模型**，直接以 `source: 'rule'` 返回结论（`unanswerable` + 原因码）；
2. **L3 校验**（`validateJudgeOutput`）拒收任何越界输出：额外字段、非枚举答案、与汤底共享 8-gram 片段、
   `yes/no/partial` 却没命中事实点（`partial` 还要求至少两条）、`unanswerable` 却没有合理原因码（"无法回答"不得当万能出口）；
3. **服务端复核**：即便模型给出 `answer`，最终答案也用 `decideFromFacts()` 按事实表重算
   （全真→是 / 全假→否 / **真假混杂→部分接近** / 未命中→无关）。

**补充说明 `explain`（可选）**：`yes / no` 时可以附一句 ≤30 字的说明，帮玩家理解这个结论的**适用范围**
（例如"否——你问的情形在本题设定中不存在"）。它受与提示文案同一套泄露检查约束：与汤底共享 8-gram、
近似抄写事实点、超长或写成反问句，都**只丢弃这一句**，判定本身照样成立 —— 一句多嘴绝不会中断整局。
`irrelevant / unanswerable` 不带说明（那两类结论本身就说明了范围）。

**提示是可选玩法**：`config.hintsEnabled` 默认 `false`，关闭时 `requestHint()` 直接返回 `HINTS_DISABLED`，
前端连按钮都不渲染。房主可在「对局参数」里随时打开（属于 `free` 项，不受"只允许增大"限制）。

**汤底揭晓仅房主可见**：`GET /api/recap` 除参与者/结算门禁外，还要求 `room.hostId === viewer`，
否则返回 `NOT_HOST`（HTTP 403）。汤底本就只在服务端注入，其他玩家的客户端里从来不存在这段文本。

**开局准备状态**：`room.ready`（成员 id 数组）记录谁点了「我准备好了」。
有资格的成员 = **非旁观且在线**（离线/旁观不会把全队卡住）；未全员准备时 `startMatch()` 返回 `NOT_ALL_READY`，
房主可用 `force: true` 强行开局（前端会二次确认"还有 N 人没准备"）。`MATCH_BEGIN` 会清空准备状态，
成员离开或被踢出也会从数组里移除，所以它永远不会跨局残留。

**房主移出玩家**：`kick` 仅房主可用、不能踢自己（要离开请走 `leave`，那会触发房主移交）。
踢人时同事务吊销该成员的会话（Worker 删 `sessions` 行、Node 清 `resume_token_hash`），
他下一次请求就是 401 被登出；房间事件里会留一条「X 已被房主移出房间」的记录，所有人都看得到。

判定缓存写在 SQLite（`verdict_cache`，主键 = 题目 + 问题哈希 + 提示词版本 + 事实集版本），
所以"同一问题永远同一答案"跨进程、跨重启都成立（`tests/integration` I-13 直接断言）。

### 3.2 回合与成员状态：两条线严格分离

- 回合线：`turn.seq` / `phase` / `deadlineAt` / `graceDeadlineAt`，超时只影响"本轮发言权"；
- 状态线：`conn`（心跳推导）与 `activity`（活动信号推导），决定投票分母与是否触发移交。

`presence.ts` 只写状态线，`turn.ts` 只写回合线；`tick()` 里先跑 presence 再跑回合，
但两者**互不写入**——`tests/core/turn.test.ts` 有两条专门断言这一点（"回合超时不改变挂机状态"、
"断连不改变挂机状态"）。房主挂机不触发移交，只有断连（心跳缺失 60s + 30s 宽限）才进入移交。

### 3.3 串行化：房间队列 + 版本号 + 唯一索引

```
WebSocket 帧 / HTTP 动作 / 定时器 tick
        └─► RoomRuntime.enqueue(task)          // 单房间串行（Promise 链）
                 ├─ 复检（队列内以最新状态为准，避免 TOCTOU）
                 ├─ reduce(room, event)          // core 纯函数
                 ├─ emit(events)                 // 分配 seq、渲染服务端文案、广播
                 └─ persist()                    // SQLite；结构性事件后补发快照
判定调用在队列之外：入队占位(JUDGING) → 出队调用 → 结果回投队列落库与推进
```

`persist()` 里写入 `state_version`；`questions` 表有 `UNIQUE(room_id, turn_seq)` 与 `UNIQUE(room_id, client_submit_id)`，
即便队列被绕过也不会产生第二次判定（I-06 验证）。

### 3.4 客户端收敛：事件流 + 快照

- 每个域事件广播 `{t:'event', seq, kind, payload, text}`，`seq` 房间内单调递增；
- **结构性事件**（回合切换、暂停/恢复、投票、移交、额度切换、AI 中断/恢复、提示、揭秘、结束）
  额外补发一份全量快照，客户端因此不需要自己推演状态就能保持一致；
- 服务端渲染所有面向玩家的中文文案（`protocol.ts` 的 `TEXT`），模型不产生任何面向玩家的自由文本。

### 3.5 客户端移动端布局：卡片排序 + 吸附输入框

桌面是两栏（左：房间 / 玩家 / 额度；右：汤面 / 记录 / 输入）。手机上直接单列堆叠时，
**左栏会排在前面**，于是「题目」和「提问输入框」被整栏玩家名单 + 一长条公共记录隔开，
读题和打字要来回滚好几屏（真实用户反馈过）。

≤900px 的规则（`index.html` 顶部那个媒体查询）：

1. `.col-main,.col-side{display:contents}` 摘掉两栏外壳，让每张卡片在盒模型上成为
   `.grid` 的直接子项，再用 `order` 排成：
   **发言者/倒计时(15) → 汤面(30) → 该你问(35) → 公共记录(38) → 输入框(40)**
   → 统计/汤主 → 结束卡/提示 → AI 创作/选题 → 房间(90)/玩家名单(92)/额度(94)。
2. 玩家卡片顺手拆开：`.speakerbox`（谁在发言 + 倒计时 + 准备按钮）置顶，
   `.memlist`（完整名单）沉底当参考信息。
3. 汤面卡片内 `.actions`（提示 T1–T3 / 提交推理·揭秘）用 `order:-1` 抬到卡片顶部 ——
   吸附的输入框会盖住卡片末尾，而揭秘是胜负手，放在下面等于被永久遮住。
4. 对局进行中（或已写草稿）时输入框 `position:sticky;bottom:0` 吸附在屏幕底部，
   边看题/边看记录边打字；吸附时收掉标题行、把记录压到 24vh，避免盖住刚判完的那条。
   `viewport` 带 `interactive-widget=resizes-content`，安卓上弹键盘时吸附条会浮在键盘之上。

**两个已经踩过的坑（都有测试钉住，`tests/web/client-render.test.ts` W4/W4b）：**

- `display:contents` 只改**盒模型**，DOM 树上卡片仍然是 `.col-main` 的子节点。
  所以排序规则**不能**写 `.grid>.composer{order:40}` —— 子选择器一个都匹配不到，
  `order` 会全部静默失效，手机上顺序毫无变化。必须用类名选择器。
- 同权重的移动端覆盖（`.card` / `.log` / `.stat` 这些）必须写在**基础规则之后**，
  否则会被后面的基础规则覆盖成没写。所以「收紧留白」那几条单独放在样式表最后。

（调试技巧：用 Edge `--headless --remote-debugging-port` + CDP
`Emulation.setDeviceMetricsOverride` 模拟 390×780 视口，`--window-size` 在 headless 下
并不会改变 `innerWidth`，截图会变成裁剪。）

## 4.5 会话代次：丢弃"离开房间后迟到的响应"

**症状**（用户报的）：单人房间里点「离开」，有时多报一个 404 / 一句"会话已失效"，必须刷新页面才能继续。

**机制**：前端每 1.2 秒轮询一次，而"最后一人离开"会让服务端**立刻物理清理房间**
（`purgeRoom` 连带删掉 sessions/rooms/questions/…）。点「离开」的瞬间很可能正好有一个
`/api/rooms/state` 在飞，它要么拿不到房间（404 `ROOM_NOT_FOUND`），要么赶在清理前拿到旧快照（200）。
这两种迟到响应都会坑人：

- 404 → 客户端写一句"连接中断（HTTP 404），正在重试…"，可此时轮询已经停了 ⇒ 这句话永远挂着；
- 200 旧快照 → `applyViewPayload` 把页面**拉回房间**，而令牌已清 ⇒ 任何操作都失败。

另外 `clearSession()` 过去没有清 `S.connected`，离开后在入口页打个字就会触发"上报活动"，
带着已经作废的令牌发请求 ⇒ 页面上冒出"会话已失效，请重新加入房间"（用户说的"多报一个错"）。

**修法**（`index.html`）：

- `sessionEpoch`：`clearSession()` 里自增；轮询/动作/启动期的会话检查都在发起前记住代次，
  回来时对不上就**整包丢弃**（不渲染、不报错、不改页面）；
- 轮询收到 **404 `ROOM_NOT_FOUND`** ⇒ `roomGone()`：回入口页 + 一句人话说明；
  其它 404（路由不存在）仍按连接问题如实报出来，避免前后端版本不匹配被伪装成"房间结束"；
- `sendAction` 在没有令牌时**静默返回**，不再往界面上写"会话已失效"；`clearSession()` 复位 `S.connected`；
- 入口页也会显示 `S.notice`，并且「创建 / 加入」（`joinOrCreate()`）会先清掉上一次会话的错误与说明。

**怎么验的**：`tests/web/client-render.test.ts` 的 W5/W6/W6b/W7/W8 用可挂起的假 `fetch`
确定性地制造"离开时请求还在飞"的窗口；另外用 CDP 把 `/api/rooms/state` 人为延迟 2.2 秒，
对**线上旧代码**能稳定复现（一次被拉回房间、一次卡在 HTTP 404），对**修好的代码**同一窗口 4/4 轮干净。

## 4.6 AI 出题失败必须能自解释

**症状**（用户报的）：房主点「AI 创作 · 生成新题」，弹出一句"操作未通过校验"，看不出到底怎么了。

**三个叠加的原因**：

1. `messageOf()` 的文案表里**没有 AI 调用失败的那些错误码**（`SCHEMA_INVALID` / `HTTP_429` /
   `HTTP_401` / `PROVIDER_REFUSAL` / `LEAK_DETECTED` …），全掉进 `default: '操作未通过校验。'`；
   而且这张表在 Worker 与 Node 服务器里**各写了一份**，两边漏的码还不一样。
2. `createAiPuzzle()` 失败时只回一个 `code`，把模型层返回的 `message`（截断预览、上游状态、内容策略）
   **直接丢掉**了，连审计都没落 —— 后台记录里查不到这次失败。
3. 出题这条路径**没有重试**：判定路径早就有 `RETRYABLE` 重试，出题却是一次定生死。
   而 `SCHEMA_INVALID` / 429 / 5xx 基本都是**一次性**的，重试一次就好。

**修法**：

- 文案表收敛成**唯一一份**（`packages/server/src/protocol.ts` 的 `messageOf`），Worker 的
  `http.ts` 只做转发；补齐全部 `ActionReject` / `SubmitReject` / `AiErrorClass` 的码；
  `default` 分支必须把码本身打出来（`操作未通过校验（未分类错误码 XXX）`），永远别再出现无信息文案。
- `createAiPuzzle()` 失败时把模型层原因放进 `detail.issues` / `detail.errors`（前端两种字段名都认），
  并落一条 `ai_puzzle_failed` 审计 —— 后台记录里能直接看到是哪一类失败。
- 出题 / 补事实点改走 `callJsonWithRetry()`：沿用 `AI_MAX_RETRIES`（默认 2）+ 400ms 递进退避。
  出题 `max_tokens` 1200 → 1800、补事实点 900 → 1200（`max_tokens` 只是上限，不额外计费）。
- **截断不再伪装成"坏题"**：`extractJsonObject` 会"补括号"救回被截断的 JSON，这对判定是好事，
  但出题的 JSON 里 `facts` 排在最后 —— 被切掉的正是最关键的字段，救回来只会得到
  "缺少 tier=1 的成立事实"这种把人引错方向的理由（审计里那条 `ai_puzzle_rejected` 就是）。
  现在：只有当"补括号"才解析成功、且上游 `finish_reason=length` 时，直接报"输出被 max_tokens 截断"。

**测试**：`tests/integration/action-messages.test.ts`（M1–M6 契约测试：每个码都要有独立文案、
表只能有一份、default 必须带 code、失败必须带 detail 与审计）；`server.test.ts` 的 I-27（真实
WS 链路：假上游返回散文 → 房主收到 `SCHEMA_INVALID` + 模型层原因，而不是"操作未通过校验"）；
`ai-generate.test.ts` 的 G7（失败一次 → 自动重试成功）、G8（截断要报 `finish_reason=length`）。

## 5. 已知的"故意简化"（不是缺陷，但要知道）

1. **内置模拟主持人靠关键词表**：它只能识别题库里写过的说法，无法处理任意自然语言改写
   （真实模型负责语义映射）。因此 `tests/integration` I-13 用的是题库脚本里的问题。
2. **无心跳即离线**：`disconnectSec = 60`。客户端必须持续发心跳（`packages/web/public/index.html` 每 20 秒一次），
   否则会被判离线——这是设计（客户端不能声明自己在线），但客户端漏发心跳会表现为"莫名离线"。
3. **`timeout_skip_enabled=false` 时不会自动跳过**，需要房主手动跳过（`skip_turn`，每局限 3 次）；
   实现里保留了这个出口，否则房间会卡死（对应《阶段5》§9 的 M-02）。
4. **移交后 20 秒自动继续**：为避免新房主也不响应导致卡死，超时自动开始下一轮。
5. **`aborted` 对局不揭晓汤底**：防止"开局 → 立刻结束 → 读汤底"的套题路径（《阶段5》§9 A5）。
